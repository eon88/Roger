### Definition of done — every milestone

- Real backend data and authorization, not just client-side simulation.
- Data scoped to authenticated Party/account IDs and least-privilege view/action permissions.
- Validations, error states and accessibility on desktop and mobile.
- Automated tests for successful journeys and unauthorized attempts.
- No sample properties/accounts added to real production data.
- Code reviewed, CI green, migration and rollback assessed before deployment.

### Architecture guardrails

1. **One authoritative record** per property, repair, work order, invoice and rent payment. Inbox aggregates tasks; it is not a competing financial database.
2. **Decisions and audit events** generated by the server, with actor, time and entity reference. A JSON-side activity feed is not immutable by itself.
3. **Agent approval** stays separate from compliance clearance and advertisement publication. Requirements depend on property/jurisdiction/tenancy stage.
4. **Contractor conversations** only expose explicitly shared work-order details; they must not reveal private landlord/tenant threads.
5. **Trade matching** is a suggestion; dispatch requires applicable verifications and human confirmation. Emergency scenarios require explicit escalation and safety guidance.
6. **Financial controls** separate invoice receipt, approval and payment recording. 'Paid' means a reconciled record, not an optimistic frontend toggle.
7. The V5 HTML is kept as a **visual/interaction reference**; do not copy it over the production site. Evolve Roger's actual role-specific frontend and stdlib backend in reviewable increments.

## Recommended first implementation slice (M1)

1. Convert the design tokens, responsive shell, list/detail layout and actionable status badges into reusable static assets without bringing over demo-only role switching.
2. Serve the Agent Inbox using the existing authenticated, scope-enforced cases, registrations, jobs and approvals as the source of truth.
3. Add deterministic task types and next-action permissions on the server.
4. Add integration and browser tests for one real inbox action and one denied cross-role action.
5. Run in an isolated staging environment, compare against the V5 reference screenshot and get user acceptance before moving to M2.
